# Ember Browser WebApp mode

Launch the installed browser with `--webapp-id=ID --webapp-url=HTTPS_URL --webapp-name=NAME` and optional `--webapp-private`. ID contains 1–64 ASCII letters, digits, `_` or `-`. URL must be HTTP(S) without credentials or control/space characters; name is nonempty and at most 200 characters. Normal mode uses `<appData>/Ember Browser/webapps/<ID>`; private mode uses the separate `webapps-private/<ID>` namespace and in-memory sessions for every tab. A second launch with the same ID and privacy mode focuses its existing window. If its address changed, a dialog asks the user to close and reopen the app; a changed name does not block focus. Arbitrary additional switches are rejected; the standard X11/GPU launcher switches remain supported. Normal Browser startup is unchanged.

Implementation keeps the Browser lifecycle, blocker startup gate, permission/download/navigation handling, and hidden chrome handshake; the content view fills a native-framed window. Startup ignores saved tabs, uses a private startup page when selected, then opens only the requested URL after the blocker decision. Blocker errors remain visible in the startup page.

Use `ember-browser --webapp-clear=ID` after closing the application to remove its normal and private profile directories. Launches hold a shared per-ID flock across exec; clear requires an exclusive lock and fails while either mode is running. The stable lock file remains for reuse, and existing Chromium singleton entries prevent cleanup until resolved. Ordinary Browser and other IDs are retained.

Native acceptance with Browser 1.46.0nb11 used an isolated HOME and loopback fixture in XWayland. It checked the expected WM_CLASS and title, page navigation, Back and Reload; one same-ID window; cross-ID cookie isolation; private cookie loss and normal cookie persistence after restart; and a same-origin popup-to-opener message. The preceding nb10 run included scoped screenshots reviewed for readable content and controls; nb11 preserves that rendering path. The nb11 run also proved that Electron retains the shared flock, rejects clear while active, and clears both profiles after graceful shutdown while retaining another ID. The real user profile was not inspected; isolated ordinary-profile sentinels remained unchanged.

The test did not establish same-ID focus visually, native menu tab selection, popup visibility or OAuth navigation. Downloads, permission prompts, external schemes, failure/retry UI and resize need their own target coverage. Do not infer these scenarios from unit tests or the loopback run.

The native test sources are `tests/webapp-mode-native.py` and `tests/webapp-x11-ui.c`. Build the helper for the target with the selected SDK compiler, sysroot and target X11/XTest/XComposite libraries. In a controlled desktop session run the target Python with `--browser <installed-wrapper> --helper <helper> --sdk <SDK-client.pyz-or-module-root> --output <new-absolute-directory> --content-offset-y <pixels> --runtime-path <target-PATH>`. The fixture uses a separate temporary HOME and owns only the processes it launches. Screenshot visibility requires human review.
