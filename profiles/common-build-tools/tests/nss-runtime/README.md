# NSS runtime smoke test

This public C consumer targets NSS 3.132 and NSPR 4.40. The Python runner
cross-builds it with GCC 16.2.0 and the explicit SDK API 1. Run the resulting
binary on an EmberBSD target after the ordinary NSS and NSPR runtime packages
are installed.

The build uses C11 and treats format warnings as errors. The lifecycle count is
unsigned to match the `%u` format in the success message.

The test performs 100 complete `NSS_NoDB_Init(NULL)` / `NSS_Shutdown()`
lifecycles. Each cycle checks the exact runtime version, accepts NSS 3.132 and
rejects the future version 3.133, requests the internal PKCS #11 slot, hashes
`abc` with SHA-256 against the independent expected bytes embedded in this
test, checks that a negative digest length is rejected as
`SEC_ERROR_INVALID_ARGS` without changing the output buffer, and requests 32
random bytes between canaries. The test checks the RNG status and that it does
not write outside the requested length. It accepts any generated byte pattern
and makes no statistical claim.

The test does not initialize a database, read credentials, access the network,
or make a TLS or FIPS claim. `NSS_NoDB_Init` receives a null path. In the
pinned implementation, it calls `nss_Init` with database, module-database,
and root-initialization flags set to skip those stores. The successful
`PK11_GetInternalSlot`, digest, and random calls exercise NSS's dynamically
loaded internal softoken and its FreeBL backend. With the ordinary packages
installed, `run.sh` clears the environment and uses the target runtime paths.

The required runtime payload for this test is:

- NSS 3.132: `lib/nss/libnss3.so`, `lib/nss/libnssutil3.so`,
  `lib/nss/libsoftokn3.so`, and `lib/nss/libfreebl3.so`.
- NSPR 4.40: `lib/nspr/libnspr4.so`, `lib/nspr/libplc4.so`, and
  `lib/nspr/libplds4.so`.
- GCC 16 target runtime: `libgcc_s.so.1` from the matching GCC16 runtime
  package if the linked ELF lists it in `DT_NEEDED`.

The NSS package's other SSL, S/MIME, DBM, and root-certificate modules are not
exercised by this test. The runner checks the installed package manifests and
the seven required ELF files for the expected target machine, ELF64 little
endian format, and SONAMEs. The target shell script checks the direct NSS and
NSPR loader paths with an empty environment before running the lifecycle test.
The lifecycle check exercises the runtime-loaded softoken and FreeBL files.
The target build and runtime execution remain separate acceptance gates.

Prepare the consumer on the development host. Use absolute paths for all
inputs and a new output directory. The selected sysroot must remain unchanged
under its shared SDK lease during preparation.

```sh
python3.15 -I -S -B prepare-runtime.py \
  --sdk-source /path/to/EmberBSD-SDK \
  --ports-root /path/to/EmberBSD-Ports \
  --cross-tools /path/to/workspace/obj/cross-tools \
  --sysroot /path/to/workspace/sysroot \
  --work /path/to/new-nss-consumer --target amd64
```

Copy the resulting binary and `run.sh` to the target. Run `./run.sh` from that
directory after installing the matching runtime packages through the ordinary
package path. The runner records input hashes, compiler identity and binary
hash in `receipt.json`; it does not install packages or execute target code.

Earlier ordinary GCC16 amd64 packaging of NSS 3.129nb2 and its common host sysroot
installation pass. The archive matches the staged payload. This C consumer
also passes 100 normal and 100 UBSan-trap lifecycles on physical NetBSD 11 amd64.
That execution uses a temporary, hash-verified dependency closure and an explicit
`LD_LIBRARY_PATH`; it does not qualify target package installation or `run.sh`.
A syscall/name lookup trace confirms successful opens of all four staged NSS
libraries, including softoken and FreeBL. A changed expected SHA-256 value
fails as intended. The target temporary directory is removed after checking.

Cppcheck 2.18.0 checks the exact GCC16-preprocessed C11 target configuration.
It detects the earlier signed `%u` operand and accepts the unsigned repair.
GCC 16.2.0 `-fanalyzer` and analysis-only Clang 21 also accept the final consumer.
These checks cover this consumer, not every NSS implementation unit. UBSan
instruments the consumer only; the shared libraries are not instrumented.
Valgrind is unavailable on the selected platform and no ASan run is claimed.

Run `test-prepare-runtime-guards.py` with the selected Ports NSS recipe patch
and installed NSPR `+CONTENTS` file to check the metadata guards. The test also
rejects altered versions, missing package identities, and duplicate records.
It does not invoke GCC or modify a sysroot.

The pinned upstream LibPKIX test contains a Valgrind note about a 4-byte leak
around `NSS_NoDB_Init`. This smoke test does not prove that behavior absent or
acceptable. A supported Valgrind run remains a separate memory check; the 100
lifecycles are not a leak check.

NSS 3.132 and NSPR 4.40 package and target execution remain pending.
The common recipe patch records the current source hashes. The official
NSS 3.132 source archive has SHA256
`ee9cf4837ba801141a804321c4462ad8f452ff4314275c6d5108a6b05af227ff`.
The upstream release is
[NSS_3_132_RTM](https://firefox-source-docs.mozilla.org/security/nss/releases/nss_3_132.html).
The API expectations map to `lib/nss/nss.h`, `lib/nss/nssinit.c`,
`lib/pk11wrap/pk11cxt.c`, `lib/pk11wrap/pk11slot.c`,
`lib/pk11wrap/pk11load.c`, `lib/freebl/loader.c`,
`lib/freebl/genload.c`, and `lib/freebl/blname.c`. The pinned NSS source
uses MPL-2.0. This consumer copies no NSS implementation code and preserves
the upstream source license and authorship.
